# 插件文案与图标规范

本规范约束 `packages/*` 里每个插件的用户可见文案与图标。新插件从模板生成后，先按本规范补齐展示面，再进入功能开发和发布。

安装步骤与兼容性见 [DEVELOPMENT.md](DEVELOPMENT.md)，发布流程见 [RELEASING.md](RELEASING.md)。本规范只回答一件事，用户第一次看到和第一次使用插件时，应该看到什么。

## 三个展示面

DSH 从每个插件读取三处展示内容，它们的分工不同。

| 展示面 | 来源 | 读者任务 |
|---|---|---|
| 插件行与详情页头 | `locale/<lang>.json` 的 `meta.title` 与 `meta.description` | 搜索、判断要不要装 |
| 详情页正文 | 包根 `README.md` | 装完以后按步骤操作 |
| 图标 | 包根 `icon.svg`，通过顶层 `icon` 字段或 `./icon` 导出声明 | 在插件列表里认出它 |

`meta.title` 与 `meta.description` 在插件未启用时也会被读取。它们不是 README 的摘要，而是插件在列表里的名片。

当前仓库不声明 `meta.detail`，详情页正文直接使用包根 README，所以 README 就是用户手册，不能只放一句介绍。以后如果给插件加功能图，按 DSH 的一图规则单独决定，README 仍然是用户手册。

`docs/` 面向维护者，放架构、命令、故障对照与设计取舍。用户需要的安装、配置、操作与卸载步骤必须写进 README。

## 名称规则

`meta.title` 是插件的显示名。它要短、稳定、可搜索，并且按语言本地化。

- 中文 4 到 12 个字符，英文 2 到 5 个单词，英文用句首大写。
- 不写版本号、草稿标记、`插件` 后缀、包 scope 或括号补充。
- 名称要包含用户会用来搜索的词，例如产品名、对象名或动作名。
- 名称一旦随插件发布就保持稳定。改名前先考虑用户已经形成的记忆。

包名与 loader id 是技术身份，不能为了配合显示名而改名。插件安装过以后，loader id 还被用户配置引用。显示名可以和侧栏入口标签不同，但描述必须用侧栏的准确标签把两者连起来。

以 jira-worklogs 为例，显示名是「Jira 工时记录」，侧栏入口标签是「Jira 日志」，描述里直接出现「Jira 日志」这个标签。

### 反例

- `Jira 工时记录（草稿）`。括号补充不是名称的一部分。
- `Jira工时记录插件`。没有空格，带了 `插件` 后缀。
- `@westwall/dsh-jira-worklogs`。包名不是用户语言。
- `强大的 Jira 工时助手 v2`。营销形容词和版本号都不该出现在名称里。

## 描述规则

`meta.description` 用一到两句话回答三件事。

第一句写用户面对的问题或目标，并带上可搜索名词。用户为什么会需要这个插件，涉及哪个产品、对象或动作。

第二句写插件带来的结果或亮点，再补入口位置、关键动作、安全边界或次要能力。会写入外部系统的插件要说明需要显式确认。需要配置的插件要说明前置条件。只读插件要写明只读。

### 约束

- 第一句控制在约 40 个中文字符以内，整段控制在约 120 个中文字符以内；英文控制在约 35 个单词以内。
- 不用营销形容词，不写版本号或内部迭代编号，不写安装步骤，不堆功能清单。
- 至少写一个可验证的亮点。亮点要说明用户因此少做什么，或者多得到什么，不要只写「支持」。
- 自动起草不等于无人值守。写入类插件要写清人工确认点，不要把需要确认的流程写成自动记录。
- 同一个插件在所有语言里的标题与描述保持相同含义。
- 描述里的 UI 标签必须和界面完全一致。

### 模板

```text
{用户面对的问题}。{插件带来的结果与一个可验证的亮点}；{入口与安全边界}。
```

### 正例

```text
手动补 Jira 工时容易漏记。打开侧栏「Jira 日志」，按天查看缺口和 Git 提交，自动起草说明，确认后查重写入；也能只读查看同事日志作参考。
```

### 反例

```text
强大的 Jira 工时助手 v2，支持月历、日详情、生成、提交、查询，一键提升效率。
```

反例的问题有三个。第一句没有说明用户面对的问题。功能清单让用户无法判断它解决什么。营销词与版本号在插件列表里没有信息量。

## README 规则

README 同时是 DSH 详情页正文和 GitHub 仓库首页。它要能让用户从零开始完成一次真实操作。

### 结构

1. H1 写成 `<标题> 使用手册`，不要直接复制显示名。
2. 草稿阶段先放状态提示条，说明是否发布、推荐哪种安装方式。
3. 用一到三句话写清问题、亮点与承诺，然后进入 `## 快速开始`。
4. 正文按用户动线组织，不按代码模块组织。

### 必须包含的章节

- `## 快速开始`
- `## 配置`
- `## 日常使用`
- `## 故障排查`
- `## 卸载与清理`
- `## 相关链接`

### 可选章节

- `## 配置参考`
- `### 维护者文档`
- `### 许可`

### 写法

- 第一屏必须说明插件解决什么问题，至少写一个可验证的亮点。
- UI 标签用中文直角引号包起来，例如「Jira 日志」「生成日志」「提交」。
- 命令放进代码围栏，一条命令只做一件事。
- 每个步骤写清预期结果，用户能判断自己是否成功。
- 段落短，表格窄。表格列数控制在三列以内。
- 关键步骤直接写进 README。DSH 详情页会把相对链接渲染成纯文本，不能把关键操作只放在 `docs/` 的相对链接后面。
- 不写凭据、私有服务地址、本机绝对路径、内部人名、验收记录或迭代编号。
- 架构、命令细节与设计取舍留在 `docs/`。
- 不用 HTML 注释。DSH 详情页会剥掉原始 HTML。

### 骨架

````markdown
# <标题> 使用手册

> **状态：草稿。** <是否发布、推荐安装方式。>

<问题、亮点与承诺。先写用户面对的问题，再写插件带来的结果和一个可验证的亮点。>

## 快速开始

1. <安装>
2. <重启或启用>
3. <配置>
4. <打开入口，预期首屏>

## 配置

| 项 | 说明 |
|---|---|
| <配置项> | <含义、默认值与前置条件> |

## 日常使用

### <主流程>

<用真实 UI 标签写步骤与预期结果。>

## 故障排查

| 现象 | 先查 |
|---|---|
| <现象> | <原因与动作> |

## 卸载与清理

<移除方式、可选的数据清理、需要撤销的凭据。>

## 相关链接

<作者主页、插件仓库、更多插件、维护者文档、许可。>
````

## 图标规则

图标是独立资源，不写进 locale，也不从 README 生成。放在包根 `icon.svg`，用 `package.json` 顶层 `icon` 字段或 `./icon` 导出声明。两者同时存在时顶层字段优先。

本节依据 DSH 自带的插件美术与清单说明整理，规则来源是 `dsh-doc` 的 `references/artwork.md` 与 `references/host-plugin.md`。

DSH 接受 SVG、PNG、JPEG、WebP，单个文件不超过 256 KiB，文件必须留在包内。绝对路径、URL 和指向包外的符号链接会被拒绝。`files` 要包含图标文件。图像无法解码时会回退到面板默认图。

### 绘制要求

- 使用 `width="36" height="36" viewBox="0 0 36 36"`。
- 背景透明，只画一个主体。插件管理器会画外围的方形底板，图标本身不要再画一层底板。
- 主体居中，留出明确边距。
- 不写字，不放脚本、事件处理器、`<style>`、`<image>`、`foreignObject`，不做动画。
- 颜色克制，用平面填充或短渐变。不要发光、投影、高光或 emoji。
- 主体超过一个时，用比例、轮廓或配色区分，不要堆徽章和面板。

### 检查方式

把图标放进真实的插件列表和详情页，按列表行尺寸与卡片尺寸各看一遍，浅色与深色主题都要看。确认图像能解码、边缘不裁切、留白不脏。

jira-worklogs 的日历加对勾图标是正例。一个日历主体，一个对勾，两色平面填充，在 36 单位画布上留出边距。新增插件可以沿用这种处理方式，不要复制它的具体形状。

已有图标明确违规时，只做最小修正，不重画。例如只调整画布尺寸、去掉底板或缩小主体。重画属于另一个决定，需要单独确认。

## 链接与互推

每个插件的 README 以 `## 相关链接` 结尾，至少包含作者主页与插件仓库。

- 作者主页 [github.com/westwall586](https://github.com/westwall586)
- 插件仓库 [dsh-westwall-plugins](https://github.com/westwall586/dsh-westwall-plugins)

在 `## 相关链接` 下加一个短的 `### 更多插件` 小节，指向仓库并给出固定提交的安装命令。

```sh
dsh plugin --profile <profile> add \
  "git+https://github.com/westwall586/dsh-westwall-plugins.git#<commit>&path:/packages/<插件目录>"
```

`<commit>` 是 40 位提交 SHA，`<插件目录>` 是包目录名。不要在每份 README 里重复维护一份会增长的插件清单，清单只在仓库根 README 维护。

私有 Jira、Git 或其他内部服务地址属于插件配置，不写进 README。README 只写占位示例，例如 `https://jira.example.com`。

`### 许可` 写一行，指向仓库 LICENSE。插件包不复用根许可证以外的许可文本。

## Locale 规则

每个插件同时提供 `locale/en.json` 与 `locale/zh.json`。两个文件的 `meta.title` 与 `meta.description` 都必须非空。

- 两种语言的标题与描述表达同一件事，不各自发挥。
- 英文标题用句首大写，只有首词和专有名词大写。
- 描述里的 UI 标签必须和界面完全一致。界面还没本地化时，英文描述保留实际显示的中文标签，并在客户端本地化后同步；不要写一个界面上不存在的英文标签。
- README 目前用中文写。插件面向英文用户发布时再补英文 README。英文 README 不是当前发布的阻塞项。
- 不要把 README 正文复制进 locale。locale 只放标题与描述。

### 以 jira-worklogs 为例

```json
{
  "meta": {
    "title": "Jira worklogs",
    "description": "Manual Jira worklogs are easy to forget. Open 「Jira 日志」 to see gaps and the day's Git commits, auto-draft entries, then confirm a deduplicated write; coworker worklogs are read-only."
  }
}
```

## 发布前检查

在插件页和真实宿主里逐项确认。

- [ ] 插件行显示正确的标题与描述，没有被截断。
- [ ] 详情页头显示同一组标题与描述。
- [ ] 详情页正文是 README，第一屏能看到状态、问题、亮点、承诺与快速开始。
- [ ] 图标在列表行与卡片尺寸都清晰，浅色与深色主题都没有问题。
- [ ] `locale/en.json` 与 `locale/zh.json` 都有非空的标题与描述。
- [ ] 标题与描述里没有版本号、草稿标记、`插件` 后缀、scope 或营销词。
- [ ] README 包含六个必需章节，命令与 UI 标签和代码一致。
- [ ] README 没有凭据、私有地址、本机路径、内部人名与验收记录。
- [ ] `## 相关链接` 含作者主页、插件仓库、`### 更多插件` 与许可证。
- [ ] 图标文件在 `files` 里，格式与大小符合 DSH 限制。

### 反模式

- 把功能清单当描述。
- 只写功能，不写用户面对的问题和插件亮点。
- 把 README 写成 CHANGELOG 或验收记录。
- 用 `插件` 后缀或版本号区分草稿。
- 在 README 里贴真实 Jira、Git 地址或账号。
- 把关键步骤只放在相对链接里。
- 每个 README 各维护一份插件清单。
- 用发光、渐变堆叠或文字做小图标。

### 以 jira-worklogs 为例

- 显示名「Jira 工时记录」，英文「Jira worklogs」。
- 描述先写手动补工时容易漏记的问题，再写缺口与 Git 提交自动起草、确认后查重写入、只读同事日志。
- README 用「Jira 工时记录 使用手册」作 H1，正文覆盖安装、配置、月历、生成、提交、暂存、素材、查询、故障与卸载。
- 图标是日历加对勾，单主体，透明背景。
- 相关链接含作者主页、仓库、`### 更多插件`、维护者文档与许可证。

## 强制执行

模板与脚手架已经带上这套结构。

- `templates/hello/README.md` 是可复制的骨架，占位符需要逐项替换。
- `pnpm create-plugin <name>` 生成新包后，先按本规范补 `locale/*.json`、README 与图标，再进入功能开发。
- 未来可以增加 `scripts/check-plugin-copy.mjs`，在 CI 里检查机械项。它可以检查 locale 文件是否存在且非空、标题与描述长度、README 必需章节、图标尺寸与体积、相关链接、以及凭据与私有地址的常见模式。本次改动不创建这个脚本。

维护这份规范时，先改规则，再改模板与已有插件。规则与实现不一致时，以本规范为准，并在同一个改动里修正模板与示例。
